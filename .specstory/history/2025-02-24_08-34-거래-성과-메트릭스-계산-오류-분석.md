## 거래 성과 메트릭스 계산 오류 분석 (2/24/2025, 8:34:56 AM)

_**User**_

요약하자면, **“테이블에는 분명 profit > 0인 매도 거래가 있는데도 Win Rate는 여전히 0%”**가 발생하는 가장 흔한 원인은 **실제 코드에서 Win Rate를 계산할 때 `successful_trades` 목록이 비거나**, 해당 트레이드가 “성공 / 매도”로 카운트되지 못하기 때문입니다.  

특히 다음과 같은 “불일치”가 대표적인 사례입니다:

1. **`success`가 파이썬 `True`(부울) 아닌 문자열 `"TRUE"`**  
   - 예: `if t["success"]:` 구문은 파이썬에서 `t["success"] == True`를 기대하지만, 실제로는 `"TRUE"` (대문자 문자열)이 들어 있어 조건을 통과 못함 → 결국 `successful_trades`에 포함 안 됨.

2. **`type` 필드가 `"sell "` (공백포함), `"SELL"`, `"sell\n"` 등으로 되어 있어**  
   - 코드에서는 `if t["type"] == "sell":` 처럼 정확히 `"sell"`만 매칭하는데, 실제로는 공백이나 대소문자 불일치 등으로 실패해서 “매도 트레이드”로 인식되지 않음.

3. **`profit` 값이 실제로는 문자열**(예: `"$30.24"` 또는 `"30.24"`)이라, 숫자 비교(`>= -fee`) 시 캐스팅을 안 해서 무효가 되어버림.

4. **한쪽 코드(로그)는 수정되어 실제 profit이 +로 찍히지만, 실제 `_calculate_metrics()`에 넘어가는 `trades`**는 업데이트 전 데이터인 경우

## 1. `success` 항목이 문자열 `"TRUE"` vs 파이썬 `True`

파이썬 딕셔너리의 `t["success"]`가 실제로 `True`(불 자료형)이 아닌 `"TRUE"`(문자열)일 때:

```python
successful_trades = [ t for t in self.trades if t["success"] ]
```
- 이 코드는 `if t["success"]` == `True`를 기대
- 하지만 `"TRUE"`(문자열)는 파이썬에서 truthy로 간주되긴 하지만, **strict 비교**에서 “불 자료형 `True`”와 다르고, 또 어떤 경우에는 `bool("TRUE") == True`여서 통과될 수도 있으나, 반대로 `if t['success']: ...` 구문이 동작하더라도, 그다음 로직에서 문제될 가능성도 있습니다.

가장 안전한 방법은, **트레이드 딕셔너리를 만들 때** `trade["success"] = True` (파이썬 불 값)로 확실히 저장하도록 하거나,  
또는 `_calculate_metrics()`에서
```python
successful_trades = [t for t in self.trades if str(t.get("success", "")).lower() == "true"]
```
처럼 강제 변환하여 필터링하는 방법도 있습니다.

---

## 2. `type` 필드가 정확히 `"sell"`인지

윈 레이트 계산 로직:
```python
if t["type"] == "sell" and t["profit"] >= -t["fee"]:
    # profitable sell
```
만약 테이블에 `"SELL"` 또는 `"sell "`(공백)처럼 기록되면 `t["type"] == "sell"` 비교가 실패하여 카운트되지 않습니다.

특히 중간에 strip() 처리를 안 했다면 `"sell "` 같은 값은 그대로 불일치가 됩니다.  
**해결**: `trade["type"] = "sell".strip().lower()` 식으로 통일하거나, 비교 시 `t["type"].strip().lower() == "sell"`로 처리.

## 3. `profit`이 문자열인지, 숫자인지

윈 레이트를 계산하는 코드:
```python
if (t["type"] == "sell" and t["profit"] >= -t["fee"])
```
- 여기서 `t["profit"]`와 `t["fee"]`가 float(예: 30.24, 2.06)이면 괜찮지만, 
- 만약 `"$30.24"` 같이 `$`가 붙은 문자열이면 **파이썬이 숫자 비교** (`">="`) 시 오류 또는 무시하게 됩니다.  
- “로그에는 30.24로 찍히지만, 실제 딕셔너리에는 `"$30.24"`가 들어있는” 상황이라면, 코드상 `30.24 >= -2.06`이 아니라 `"30.24" >= "-2.06"`을 비교하려 하여 결국 false가 되거나 예외가 날 수 있습니다.

따라서 **실제로 `trade["profit"]`에 들어가는 값이 float**인지, 혹은 **문자열**인지(포맷팅이 이미 적용된 값인지) 확인이 필요합니다.  
보통 `execute_trade()` 메서드에서
```python
profit = revenue - cost_portion - fee  # float
trade["profit"] = profit
```
로 저장하므로, 숫자(float)일 것 같지만,  
만약 어느 과정에서 “테이블 표시를 위해 ‘$30.24’ 문자열로 변환한 DataFrame”을 다시 `trades`에 반영해버린다면, 문제가 생길 수 있습니다.

## 4. 확인 및 해결법

1. **로그에서 “Profitable sell trade found”**는, 예를 들어 이런 코드가 있을 수 있습니다:
   ```python
   for trade in trades:
       if trade["type"] == "sell" and trade.get("profit", 0) > 0:
           logger.info("Profitable sell trade found: fee=%.2f, cost=%.2f, revenue=%.2f, profit=%.2f", ...)
   ```
   - 이 로그는 “문자열”이 아니라, 실시간 코드 상 `float` 비교로 찍힌 정보일 뿐 → 백테스터 최종 `_calculate_metrics()`는 동일 데이터 구조를 보지만, 
   - **조건이 안 맞아서**(`success`가 `True`가 아니거나, `type`이 공백, profit이 문자열…) `profitable_trades`에 못 들어갈 수 있음.

2. **테스트**:  
   - `_calculate_metrics()` 직전에, `print([ (t["type"], t["profit"], t["fee"], t["success"]) for t in self.trades ])`  
   - 이걸로 실제 자료형, 값이 어떻게 되어있는지 확인.  
   - “success”가 `True`(bool)인지 `"TRUE"`(str)인지, “type”이 `"sell "`(공백)인지 `"sell"`인지, “profit”이 float인지 string인지 직접 찍어 보면 됩니다.

3. **수정**:  
   - `trade["success"] = bool_value` 로 확실히 저장 (파이썬 bool).  
   - `trade["type"] = "sell"` (소문자, strip).  
   - `trade["profit"] = float(...)`.  

4. **Win Rate가 실제로 높아질 것**:  
   - 이익인 매도 거래( profit>0 )가 “success==True” & “type==sell” 로 인식되면, `profitable_trades`가 증가 → Win Rate > 0%.

## 5. “Max Drawdown 429%, Total Return -418%” 등 포맷 오차

로그 마지막에 보면:
```

- Sharpe Ratio: -0.726
- Max Drawdown: 429.21%

```

- 마찬가지로 4.29% drawdown을 429.21%로 표시.  
이건 `_calculate_metrics()`에서 이미 *100을 곱한 값( -4.18 )*을 “%.2f%%”로 다시 포매팅 → -4.18 → “-418.00%” 가 되는 식으로 중복.

해결: 
1) `_calculate_metrics()`가 return할 때는 -4.18 처럼 “실제 퍼센트 값”으로 두고, UI 표시에서 `f"{total_return:.2f}%"`로 하면 “-4.18%” 나옴  
혹은  
2) `_calculate_metrics()`가 -0.0418(소수)로 두고, UI에서 100을 곱해 출력.

지금 코드에서는 `_calculate_metrics()`에서 `total_return`을 `-4.1807`로 리턴하나, 로그 찍을 때 “%.2f%%”를 적용하는 바람에 -4.18 → -418.00%로 보이는 식입니다.

## 결론

- **Win Rate = 0%** 문제는 대부분 “성공 트레이드가 `t["success"]`가 진짜 bool True인지, `type`이 `"sell"`이 맞는지, `profit`이 float인지” 등에서 불일치가 있어서 발생합니다.  
- **테이블에 양수 profit이 보여도, code 측에서는 그 거래를 “success=False” 또는 “type != 'sell'” 등으로 처리**할 수 있으니, 실제 `_calculate_metrics()`를 호출하기 전의 `trade` 딕셔너리 구조를 **그대로 프린트**하여 검사하세요.

또한,  
- `Max Drawdown`, `Total Return`이 너무 크게 표시된다면, **출력 포맷에서 추가로 x100 해버린 중복**이 원인입니다.  
- `_calculate_metrics()`는 “-4.18”을 반환하지만, UI가 다시 `f"{val}%"` 처리로 “-418%”가 되는 것이라면, 한쪽만 수정하면 됩니다.

_`_calculate_metrics()` 내부의 로직_ (또는 Win Rate 계산하는 코드)에서는 그 트레이드를 **“success==True이면서 type=='sell'이고, profit >= -fee”** 등등의 조건을 만족하지 못해서  
**“이익이 난 트레이드”**로 카운팅하지 않는 상황입니다.

---

## 1. 가장 흔한 원인들 다시 정리

1. **`success`가 bool `True` 아닌 `"True"`(문자열) 문제**  
   - 예) `if t["success"]:` 구문에서 파이썬이 문자열 `"True"`를 truthy로 인식하기도 하지만,  
     내부에서 `t["success"] is True` 비교나, 추가 로직으로 `str(t["success"]).lower() == "true"`를 안 하면, 잘못 처리될 수 있음.  
   - 해결: `trade["success"] = True` (bool)로 명시하거나, Win Rate 계산 때 `str(...).lower() == "true"` 등을 써서 처리 일관성 확보.

2. **`type` 필드에 불필요한 공백/대소문자**  
   - 예) `"Sell"`, `"SELL\n"`, `"sell "` 등.  
   - Win Rate 계산 로직에선 `if t["type"] == "sell": ...` 처럼 딱 `"sell"`만 매칭.  
   - 해결: `trade["type"] = trade["type"].strip().lower()` 식으로 정규화.

3. **`profit`/`fee`가 문자열**  
   - 예) `"$2.44"`, `"$1,199.00"`, `"1.23"` 등 → Win Rate 계산 시 float 비교를 못하거나, 잘못된 비교가 이뤄짐.  
   - 해결: `trade["profit"] = float(...)`, `trade["fee"] = float(...)` 로 **숫자 변환**.  
   - 또한 “수수료가 `$0.25`”와 같은 문자열이 남아 있으면, `profit >= -fee` 에서 비교가 실패하거나 예외 발생.

4. **“매도” 또는 “이익 실현”으로 인식되는 조건이 실제로는 달라서**  
   - 예) Win Rate 계산 코드에서 `(t["type"] == "sell" and t["profit"] >= -t["fee"])`라고 가정했는데, 실제론 “buy 후에 포지션이 올랐을 때”도 승리로 치게끔 만들었다면?  
   - 혹은 “PnL 계산은 매도 시점에만 `profit` 반영하는 구조”에서, agent가 buy만 잔뜩 했다면 대부분 “Win = 0”이 될 수도 있음.

---

## 2. 확인 방법

**“테이블에는 profit이 +인 SELL 기록이 있는데, 왜 Win Rate는 0?”**을 해결하려면, 

1. **`_calculate_metrics()`** 바로 직전, 혹은 그 안에서:
   ```python
   for t in self.trades:
       print(t["type"], t["success"], t["profit"], t["fee"])
   ```
   - 실제로 각 트레이드에 어떤 값들이 들어있는지 (자료형/문자열/공백 포함) 확인

2. 확인 후,  
   - 만약 `t["type"] == "sell "`(공백) 같은 게 있으면 `strip().lower()` 처리,  
   - `t["success"]`가 `"TRUE"`(문자열)이면 bool로 변환,  
   - `profit`/`fee`가 `"$12.34"` 같은 문자열이면 float로 치환,  
   - 이런 식으로 데이터 정규화를 확실히 해 주어야 합니다.

3. 그럼 실제로 `profit > 0` & `type="sell"` & `success=True` 를 만족하는 트레이드가 발견되면, Win Rate 계산에서 count될 것입니다.

---

## 3. 어떻게 고치면 되는가?

이미 답변에서 제시한 식으로, `_calculate_metrics()`에서:

```python
# 예시
success = str(t.get("success", "")).strip().lower() == "true"
trade_type = str(t.get("type", "")).strip().lower()

try:
    profit = float(str(t.get("profit", "0")).replace("$", "").replace(",", "").strip())
    fee = float(str(t.get("fee", "0")).replace("$", "").replace(",", "").strip())
except:
    profit, fee = 0.0, 0.0
```

이런 식으로 **강제 변환**하여, Win Rate 로직에서:

```python
if success:
    # ...
    if trade_type == "sell" and profit >= -fee:
        profitable_trades_count += 1
```

이런 로직으로 처리하면 **분명히** profit>0인 매도 거래가 잡히면 Win Rate > 0%가 됩니다.

또한, **execute_trade()** 내에서 애초에 `trade["success"] = True` (bool)로, `trade["type"] = "sell"`, `trade["profit"] = float(...)` 등으로 저장하면,  
나중에 정규화 로직 없이도 깔끔하게 계산됩니다.

## 4. 마무리 요약

- **로그**에서 `Profitable sell trade found: ... profit=xx`라고 찍히는 이유는 분명히 “profit이 +”라는 걸 알지만, **Win Rate 계산**에선 해당 항목이 “success=False”로 분류되거나, `type='sell '`(공백) 등으로 불일치하면 카운트가 안 됨.  
- **해결**: (A) trade dict를 처음부터 확실히 bool/float로 저장, (B) `_calculate_metrics()`에서 강제 변환/정규화, (C) Win Rate 로직에서 “sell”인 경우만 체크하기 전 `strip().lower()`로 맞춤.  
- 이 과정을 마친 뒤, 같은 데이터셋으로 backtest를 해 보면, 분명히 Win Rate가 0%가 아니라 일정 비율(예: 15%, 30% 등)로 올라갈 것입니다.  

결론적으로, **데이터 정규화**(success, type, profit, fee)가 핵심이며, 한 번 디버깅(`print(t)`)으로 실제 트레이드 딕셔너리가 어떻게 들어오는지 확인하면 금방 원인을 찾으실 수 있습니다.

## 1. 왜 Win Rate 0.0이 최종 로그에 찍힐까?

여기서 단서를 보면,
- 최종 로그에 **`'avg_trade': 0.0`** 같은 키가 나오는데,  
- `\_calculate_metrics()` 함수 코드를 보면 `'avg_trade'`라는 키를 **전혀** 반환하지 않습니다.

즉, **`'avg_trade'`가 들어간 metrics**는 **`_calculate_metrics()`가 아닌 다른 함수**(ex. `_process_results()`, `Backtest_Results.py` 내부 로직 등)에서 만들어지고 있다는 의미입니다.

흔히 다음과 같은 패턴이 발생합니다:

```python
# BaseBacktester.run() 최종:
results = {
    "metrics": self._calculate_metrics(),
    "trades": self.trades,
    ...
}

# 그 이후 BacktestManager 나 Backtest_Results.py 같은 곳에서
some_metrics = self._process_results(results)  # 별도 함수
results["metrics"].update(some_metrics)        # => 최종 metrics가 덮어짐 or 합쳐짐
```

그 별도 함수 `_process_results()` 안에서,
```python
def _process_results(self, results):
    metrics = {}
    trades = results.get("trades", [])
    portfolio_values = results.get("portfolio_values", [])

    # 임의로 win_rate=0, avg_trade=0 등 계산 또는 기본값
    metrics["total_trades"] = len(trades)
    metrics["win_rate"] = 0.0  # ...
    metrics["avg_trade"] = 0.0
    ...
    return metrics
```

이런 식으로 **다시 `'win_rate'`를 0.0으로 설정**하고 있기 때문에,  
최종 `'results["metrics"]'`에는 `'win_rate': 0.0`가 남게 되어, 로그에도 0.0%로 찍히는 것입니다.

## 2. 해결방법

### A. **중복 계산 로직**을 제거 / 통합

- **“Win Rate, Sharpe, Sortino, Drawdown” 등 핵심 메트릭**은 `BaseBacktester._calculate_metrics()` 단 하나에서 계산하게끔 하고,  
- 다른 후처리 함수(`_process_results()`, etc.)는 중복/임의로 `'win_rate'`를 다시 계산하거나 디폴트값을 넣지 않도록 수정해야 합니다.

즉, `\_calculate_metrics()`가 반환한 `'win_rate': 0.04166...` (4.17%)를 그대로 사용하는 식입니다.

### B. 혹은 “두 로직”을 합쳐 하나로

만약 `_process_results()`가 꼭 필요한 추가 항목(예: `'avg_trade'`, `'win_rate'`, `'win_rate_long_only'`, …)을 계산해야 한다면,  
- 이때 **이미 `metrics["win_rate"]`가 존재한다면 덮어쓰지 않는다**,  
- 또는 “기존 값이 없다면 계산, 있으면 사용” 식으로 합쳐야 합니다.

예를 들어:
```python
def _process_results(self, results):
    metrics = results.get("metrics", {}).copy()  # BaseBacktester metrics
    trades = results.get("trades", [])

    # 이미 metrics["win_rate"] 있을 테니 overwrite하지 않고, 필요하면 보강
    # e.g. if "win_rate" not in metrics:
    #     metrics["win_rate"] = 0.0

    # 만약 avg_trade가 필요하다면, 추가 계산
    if trades:
        sum_profit = sum(t.get("profit",0) for t in trades if t.get("success"))
        count_success = sum(1 for t in trades if t.get("success"))
        metrics["avg_trade"] = (sum_profit / count_success) if count_success>0 else 0.0

    return metrics
```

이런 식으로 **기존 `win_rate`**를 보존하면서, 필요한 항목만 **추가**하도록 해야 최종적으로 Win Rate가 사라지거나 0이 되지 않습니다.

### C. 로깅/표시할 때는 최종 `results["metrics"]`만 사용

- 최종 백테스트가 끝나고, `'results["metrics"]'`를 로깅할 때 **바로 `_calculate_metrics()` 결과**를 보지 않고,
- 다른 함수가 `results["metrics"]`를 덮어썼다면,  
**logging할 때**도 `logger.info("Win Rate: %f", results["metrics"]["win_rate"])`가 0.0이 뜰 수밖에 없습니다.

따라서, 
1. **“진짜 최종 metrics”**를 한 번만 계산  
2. 그걸 `results["metrics"]`에 넣고,  
3. UI/로그에서도 반드시 **그 동일한** `results["metrics"]`를 사용  
이 흐름이 일관되게 보장되어야 합니다.

## 4. 출력 포맷에서 -1244% 되는 문제도 동일 원인

로그의:
```
total_return: -0.124457...
- Total Return: -1244.57%
```
또는  
```
max_drawdown: 0.1263...
Max Drawdown: 1263.63%
```

이는 **이미 decimal( -0.1244 => -12.44% )을** 추가로 “`%.2f%%`” 로 찍어버려서 “-1244.44%”가 되는 문제입니다.

- “-0.1244” (decimal) → “(-0.1244 \* 100) = -12.44%” → 로그 찍을 때 다시 `%.2f%%` => “-1244.44%”  
- 동일하게 Drawdown 0.126 → 12.6% → 또 x100 → 1260%.

**해결**:  
- `_calculate_metrics()`가 decimal 값(-0.1244) 자체를 주면, 로깅/UI에서 `value * 100`한 뒤 “%.2f%%”로 찍어야 정확히 -12.44%.  
- 지금은 중복 곱하기로 -1244.4%가 되어버립니다.

이 역시 **중복 계산** 문제이므로, 한쪽만(메트릭 계산단 or 출력단)에서 **\*100** 해야 합니다.

## 결론

> **“Win Rate가 `_calculate_metrics()`에서는 4.2%로 찍히는데, 최종 로그엔 0%로 보인다.”**  

는 곧 **“최종 로그에서 쓰는 metrics가 `_calculate_metrics()` 결과를 무시하고, 다른 코드에서 덮어쓴 값”**이라는 뜻입니다.  
- 특히 `'avg_trade': 0.0'` 같은 키가 `_calculate_metrics()`에 없는데도 최종에 등장하는 걸 보면, **두 번째 계산/합산 로직**이 존재합니다.

따라서 **“그 다른 로직”**(예: `_process_results()`, `Backtest_Results.py`에서 `results["metrics"] = self._some_other_func()`)을 찾아서,  
- “Win Rate” 계산을 제거 / 통합,

## 1. 왜 Win Rate 0.0이 최종 로그에 찍힐까?

여기서 단서를 보면,
- 최종 로그에 **`'avg_trade': 0.0`** 같은 키가 나오는데,  
- `\_calculate_metrics()` 함수 코드를 보면 `'avg_trade'`라는 키를 **전혀** 반환하지 않습니다.

즉, **`'avg_trade'`가 들어간 metrics**는 **`_calculate_metrics()`가 아닌 다른 함수**(ex. `_process_results()`, `Backtest_Results.py` 내부 로직 등)에서 만들어지고 있다는 의미입니다.

흔히 다음과 같은 패턴이 발생합니다:

```python
# BaseBacktester.run() 최종:
results = {
    "metrics": self._calculate_metrics(),
    "trades": self.trades,
    ...
}

# 그 이후 BacktestManager 나 Backtest_Results.py 같은 곳에서
some_metrics = self._process_results(results)  # 별도 함수
results["metrics"].update(some_metrics)        # => 최종 metrics가 덮어짐 or 합쳐짐
```

그 별도 함수 `_process_results()` 안에서,
```python
def _process_results(self, results):
    metrics = {}
    trades = results.get("trades", [])
    portfolio_values = results.get("portfolio_values", [])

    # 임의로 win_rate=0, avg_trade=0 등 계산 또는 기본값
    metrics["total_trades"] = len(trades)
    metrics["win_rate"] = 0.0  # ...
    metrics["avg_trade"] = 0.0
    ...
    return metrics
```

이런 식으로 **다시 `'win_rate'`를 0.0으로 설정**하고 있기 때문에,  
최종 `'results["metrics"]'`에는 `'win_rate': 0.0`가 남게 되어, 로그에도 0.0%로 찍히는 것입니다.

## 2. 해결방법

### A. **중복 계산 로직**을 제거 / 통합

- **“Win Rate, Sharpe, Sortino, Drawdown” 등 핵심 메트릭**은 `BaseBacktester._calculate_metrics()` 단 하나에서 계산하게끔 하고,  
- 다른 후처리 함수(`_process_results()`, etc.)는 중복/임의로 `'win_rate'`를 다시 계산하거나 디폴트값을 넣지 않도록 수정해야 합니다.

즉, `\_calculate_metrics()`가 반환한 `'win_rate': 0.04166...` (4.17%)를 그대로 사용하는 식입니다.

### B. 혹은 “두 로직”을 합쳐 하나로

만약 `_process_results()`가 꼭 필요한 추가 항목(예: `'avg_trade'`, `'win_rate'`, `'win_rate_long_only'`, …)을 계산해야 한다면,  
- 이때 **이미 `metrics["win_rate"]`가 존재한다면 덮어쓰지 않는다**,  
- 또는 “기존 값이 없다면 계산, 있으면 사용” 식으로 합쳐야 합니다.

예를 들어:
```python
def _process_results(self, results):
    metrics = results.get("metrics", {}).copy()  # BaseBacktester metrics
    trades = results.get("trades", [])

    # 이미 metrics["win_rate"] 있을 테니 overwrite하지 않고, 필요하면 보강
    # e.g. if "win_rate" not in metrics:
    #     metrics["win_rate"] = 0.0

    # 만약 avg_trade가 필요하다면, 추가 계산
    if trades:
        sum_profit = sum(t.get("profit",0) for t in trades if t.get("success"))
        count_success = sum(1 for t in trades if t.get("success"))
        metrics["avg_trade"] = (sum_profit / count_success) if count_success>0 else 0.0

    return metrics
```

이런 식으로 **기존 `win_rate`**를 보존하면서, 필요한 항목만 **추가**하도록 해야 최종적으로 Win Rate가 사라지거나 0이 되지 않습니다.

### C. 로깅/표시할 때는 최종 `results["metrics"]`만 사용

- 최종 백테스트가 끝나고, `'results["metrics"]'`를 로깅할 때 **바로 `_calculate_metrics()` 결과**를 보지 않고,
- 다른 함수가 `results["metrics"]`를 덮어썼다면,  
**logging할 때**도 `logger.info("Win Rate: %f", results["metrics"]["win_rate"])`가 0.0이 뜰 수밖에 없습니다.

따라서, 
1. **“진짜 최종 metrics”**를 한 번만 계산  
2. 그걸 `results["metrics"]`에 넣고,  
3. UI/로그에서도 반드시 **그 동일한** `results["metrics"]`를 사용  
이 흐름이 일관되게 보장되어야 합니다.

- `_calculate_metrics()`가 decimal 값(-0.1244) 자체를 주면, 로깅/UI에서 `value * 100`한 뒤 “%.2f%%”로 찍어야 정확히 -12.44%.

이 역시 **중복 계산** 문제이므로, 한쪽만(메트릭 계산단 or 출력단)에서 **\*100** 해야 합니다.
