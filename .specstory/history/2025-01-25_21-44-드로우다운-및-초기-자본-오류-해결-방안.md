1. test_risk_limits_in_crash 실패 (드로우다운이 0.15를 초과)

테스트에서 “Risk limits should prevent drawdown exceeding 0.15”라고 해놓았는데, 실제 백테스트 결과에서 ￼이 0.15를 초과해버립니다.

1.1. 원인
	1.	RiskManager가 드로우다운이 15%를 넘으면 ‘더 이상 롱 포지션 증가를 막는다’ 정도로만 되어 있어도, 실제 시세 하락 폭이 워낙 커서 이미 손실이 15%를 넘어버릴 수 있음.
	2.	에이전트가 계속 매수하거나, 충분히 빠르게 포지션을 줄이지 않아서 드로우다운이 커짐.
	3.	risk_manager가 “drawdown 초과 시 거래 거부”는 하고 있어도, 이미 발생한 보유 포지션의 평가손을 완전히 막지는 못할 수 있음(즉, drawdown을 ‘사후에 더 큰 매수를 막는’ 정도로는 15% 이상이 안 나올 거라는 보장이 없음).

1.2. 해결 방향
	•	(A) 에이전트 로직: crash가 발생하면 즉시 포지션을 줄이는(=매도) 로직(또는 0.0 action) 을 의도적으로 넣으면, drawdown이 제한될 수도 있음.
	•	(B) risk_manager가 강제 포지션 청산 로직을 넣는다. 예컨대 “drawdown이 15% 초과 순간, 모든 포지션을 0으로 강제 청산” → 그러면 드로우다운이 그 이상 커지지 않음.
	•	(C) 테스트 기준 완화: 만약 “백테스터 상에서 drawdown 15%를 절대 넘길 수 없게 하는 건 너무 과도한 기대”라면, 0.15 → 0.2 등으로 상향. (이미 코드에서 0.2로 바꿨더니 -0.2 미만이 안 된다는 에러가 나는 상황도 있음)
	•	(D) 시나리오 세팅 완화: crash_size를 줄이거나, crash_duration을 길게 해서 갑작스러운 급락 폭이 조금 부드러워지도록 조정.

가장 확실한 것은 (B) 강제 청산이나, (A) agent가 하락 시 매도를 유도하는 전략을 추가하는 것입니다.

2.2. 어떤 식으로 할지 결정
	•	만약 프로젝트 전체적으로 **initial_capital**이라는 이름을 쓰고 있다면, LiveTradingEnvironment도 통일해서 initial_capital로 받도록 바꾸는 게 좋습니다.
	•	반대로 LiveTradingEnvironment에서 계속 init_balance라는 이름을 고수하고 싶다면, 테스트 쪽에서 initial_capital= 호출부를 전부 init_balance=로 교체하면 됩니다.

중요한 점은 **“테스트와 실제 클래스의 인자 이름이 일치”**해야 TypeError가 사라진다는 것입니다.

결론 및 정리
	1.	Risk limit / drawdown 문제
	•	현재 RiskManager는 drawdown이 일정 수준을 넘으면 “추가 매수를 거부” 정도는 하지만, 기존 포지션이 가져오는 손실은 막지 못합니다.
	•	그러다 보니 테스트에서 15% 초과 drawdown이 발생 → 실패.
	•	￼ “강제 포지션 청산” 혹은 “agent가 하락 시 스스로 포지션 축소” 로직이 필요하거나, 테스트 기준을 완화해야 합니다.
	2.	LiveTradingEnvironment 파라미터 문제
	•	테스트가 initial_capital=를 넘기는데, LiveTradingEnvironment는 그 인자 없음 → TypeError.
	•	￼ 두 선택지 중 하나:
	•	LiveTradingEnvironment에 __init__(..., initial_capital=10000.0, ...) 추가,
	•	혹은 테스트에서 init_balance=10000.0 등 맞춤.
	3.	나머지 자잘한 부분
	•	에이전트(DummyStrategy) 액션이 ±1.0으로 아주 커서 drawdown이 쉽게 커질 수 있음(-> 더 작은 액션 or RiskManager 강화).
	•	시나리오 crash_size=0.5(50% 폭락)면 drawdown이 크게 나올 수밖에 없으므로, risk_config.max_drawdown_pct=0.3(30%)처럼 좀 더 크게 잡아주거나, crash_size를 0.3~0.4로 완화.

한마디로,
	•	“테스트가 원하는 시나리오 반응” vs “에이전트/리스크매니저 실제 구현”을 다시 맞춰보면, 나머지 실패들도 정리될 것입니다.
	•	LiveTradingEnvironment는 인자 이름만 통일하면 TypeError가 해결됩니다.

    length: int = 1000,
    crash_at: Optional[int] = None,
    crash_duration: Optional[int] = None,

    recovery_duration: Optional[int] = None,
    base_price: float = 100.0,
) -> pd.DataFrame:
    """Generate flash crash scenario data
    
    Args:
        length (int): Total number of periods
        crash_at (int, optional): Index at which crash occurs. If None, will be set to length//2
        crash_duration (int, optional): Duration of crash in periods. If None, defaults to 5
        crash_size (float): Size of crash as fraction of price (0.3 means 30% drop)
        recovery_duration (int, optional): Duration of recovery in periods. If None, defaults to 2x crash_duration
        base_price (float): Starting price level
        
    Returns:
        pd.DataFrame: OHLCV data with flash crash
    """

    if crash_at is None:
        crash_at = length // 2
    if crash_duration is None:
        crash_duration = 5  # Increased from 3 to 5
    if recovery_duration is None:
        recovery_duration = crash_duration * 2

    # Ensure crash_at has enough room for crash and recovery
    crash_at = min(crash_at, length - (crash_duration + recovery_duration))

    timestamps = pd.date_range(
        start="2024-01-01", periods=length, freq="5min"
    )

    pre_crash_returns = np.random.normal(0.0002, 0.002, crash_at)  # Slight upward trend with volatility

    prices[crash_at] = crash_price  # Immediate drop

이 문제를 해결하기 위해 확실하게 큰 드로우다운을 발생시키는 방법들을 정리해 드리겠습니다.

1. 시나리오를 완전히 결정적(Deterministic) 으로 만드는 방법

테스트에서 “flash crash 시나리오”나 “low liquidity 시나리오”를 난수 기반으로 생성하다 보면, 운이 나쁘면(혹은 좋으면) 충분히 큰 낙폭이 안 생길 수 있습니다.
이를 막으려면, 테스트용 시나리오는 완전히 고정된 데이터를 만들어주면 됩니다.

예시:

def generate_flash_crash_data_deterministic(
    length=1000,
    crash_at=500,
    crash_size=0.3,  # 30%
    base_price=100.0,
):
    """
    완전히 결정적인(난수 없는) flash crash 시나리오 생성.
    crash_at 지점에서 price가 30% 급락, 이후 살짝 회복
    """
    import numpy as np
    import pandas as pd
    
    timestamps = pd.date_range("2025-01-01", periods=length, freq="1min")
    prices = np.full(length, base_price)

    # 1) 초기 구간(0 ~ crash_at-1): 가격 서서히 10% 정도 오르도록
    for i in range(1, crash_at):
        prices[i] = prices[i-1] * 1.0005  # 미세한 상승(여기선 완전 결정적 수치)

    # 2) crash_at 시점에 30% 단번에 하락
    pre_crash_price = prices[crash_at - 1]
    crash_price = pre_crash_price * (1 - crash_size)
    prices[crash_at] = crash_price

    # 3) crash 이후 한 10칸 동안 더 낮은 가격 유지(추가 하락 5%)
    for i in range(crash_at + 1, crash_at + 10):
        prices[i] = crash_price * 0.95

    # 4) 나머지 구간은 약간씩 회복
    for i in range(crash_at + 10, length):
        prices[i] = prices[i-1] * 1.001  # 서서히 상승

    # OHLCV (open=low=high=close=이 동일) + volume은 대충 고정
    data = pd.DataFrame({
        "$open": prices,
        "$high": prices,
        "$low": prices,
        "$close": prices,
        "$volume": 100_000
    }, index=timestamps)

    return data

이렇게 하면,
	•	항상 crash_at 시점에 30% 확실하게 하락
	•	이후 5% 더 하락 구간이 10칸 존재
	•	그 결과 드로우다운이 거의 30~35%까지는 확실하게 발생.

테스트에서도 “max_drawdown이 0.2(20%) 이상”을 항상 만족하게 됩니다.

장점
	•	매 테스트 때마다 결과가 동일하므로, “낙폭이 안 나와서 실패” 같은 일이 일어나지 않음.
	•	“flash crash”를 원하는 형태로 100% 재현 가능.

단점
	•	랜덤성이 사라져서, “실제 시장 같은” 느낌이 줄어들 수 있으나, 테스트 목적으로는 오히려 결정적인 데이터가 안정적입니다.

2. 랜덤 시나리오를 쓰면서도 큰 낙폭 보장

어떤 시나리오는 일부 구간은 랜덤으로 하되, 특정 지점에서 강제로 30% drop을 삽입하면 됩니다. 예:

def generate_flash_crash_data_partial_random(...):
    ...
    # 0) 초반 ~ crash_at까지: 가벼운 랜덤 상승/하락
    # 1) crash_at 시점: 강제로 30% 하락
    # 2) 이후 구간: 다시 일정 부분 랜덤

이 경우도, crash_at에서 price를 (1 - crash_size)만큼 곱해서 완전 하락시키면, 그 시점에 반드시 큰 drawdown이 발생합니다.

3. 에이전트(또는 RiskManager)로 “충분히 큰 포지션” 유지

크게 하락해도 포지션을 전혀 안 들고 있으면 drawdown이 거의 발생하지 않습니다. 테스트에서 큰 drawdown을 원한다면,
	•	에이전트가 crash 시점 직전에 “풀 매수(±1.0)” 해놓도록(혹은 short → long 전환)
	•	그렇게 해야 시세 급락 시에 PnL 손실 → drawdown이 크게 생김.

방법
	•	DummyStrategy가 일정 구간까지는 계속 +1.0 action(풀매수) 유지 → crash 순간에 큰 drawdown 발생.
	•	또는 RiskManager가 드로우다운 초과 시점까지는 포지션 축소를 막고, 딱 crash 끝나고 나서야 포지션 해제.

4. RiskManager가 drawdown 초과 시 즉시 청산

만약 테스트가 “drawdown이 0.15를 절대 넘으면 안 됨”을 요구한다면, 실제 시장에서는 갑자기 -30% crash가 오면 15% 선에서 스톱로스가 체결되지 않을 수 있습니다(슬리피지).
그러나 테스트 목적이라면, “정말 15% 이상 가기 전에 포지션을 자동으로 강제 청산”하도록 RiskManager를 더 강하게 설정할 수 있습니다.

예시

if current_drawdown > self.config.max_drawdown_pct:
    # 즉시 전부 청산
    for sym in positions:
        positions[sym] = 0.0
    return {
        "allowed": False,
        "adjusted_size": 0.0,
        "reason": "Forced liquidation (drawdown > limit)"
    }

그렇게 하면, 시가 급락으로 실제 -20%까지 손실이 갈 수 있는 현실과는 달리, 테스트 상에서는 15% 이상 손실이 안 나도록 “가상”으로 막아줄 것입니다.

5. 테스트 자체에서 기준을 완화
	•	만약 “30% 크래시” 시나리오인데 에이전트가 빨리 손절해서 실제 drawdown이 0.05(5%)로 그친다면, 테스트에서는 “0.2 넘는 drawdown 기대했는데? 실패”가 뜹니다.
	•	하지만 실제로는 “빨리 손절 잘했네!”가 될 수 있죠.
→ 즉, 테스트가 “무조건 0.2 이상의 drawdown이 나야 한다”고 기대하는 게 맞는지 재검토해야 합니다.

종합 정리: “드로우다운이 커야 통과” 테스트를 확실히 통과시키려면?
	1.	결정적 시나리오 + 강제 풀 포지션
	•	시나리오: 100 → crash_at에 70(30% 하락), 그 후 60까지 추가 하락
	•	에이전트: 그 시점까지 계속 풀매수(1.0)
	•	→ 실제 drawdown은 40% 이상 확정 → 테스트 통과.
	2.	RiskManager로 drawdown 강제 “<= 0.15”
	•	시가가 30% 급락해도, RiskManager가 “15% 넘어가면 바로 청산” → 실제 최종 drawdown 15% 이하.
	•	테스트가 “0.15 이하”를 요구하면 통과.
	3.	테스트 기대치 조정
	•	만약 “드로우다운은 0.1(10%) 이상” 정도면 충족 가능하지만 0.2(20%)는 좀 과하다 싶으면 낮춘다.

마무리

이처럼, 테스트가 원하는 “극단적 조건(큰 낙폭 or 반대로 낙폭 제한)”을 확실히 재현하려면,
	•	시나리오를 완전 결정론적으로 만들거나,
	•	에이전트와 risk_manager가 해당 결과를 반드시 유도하도록 로직을 합의해줘야 합니다(예: 풀매수 or 강제 청산 등).

지금처럼 난수 기반으로 큰 하락을 “매번” 기대하기는 어렵고, 에이전트가 항상 풀포지션을 들고 있어준다는 보장도 없으니, 테스트가 자주 실패합니다.

가장 추천:
	•	**테스트 용 “deterministic scenario”**를 하나 더 만들어서, crash가 반드시 -30% 이상 나게 하고(포지션도 보유), 그로 인해 drawdown이 0.2 이상 찍히거나 / 또는 risk_manager가 0.15 이상 되기 전에 청산하게 하여, 원하는 테스트 케이스를 확실히 통과시키는 식으로 처리하면 좋습니다.
	•	“진짜 랜덤 시나리오”는 회귀 테스트에는 부적합하고(결과가 매번 달라질 수 있음), 주로 시뮬레이션 연구 목적에 쓰는 편이 낫습니다.

이런 식으로 하시면 “매번 무조건 드로우다운 0.2 이상”을 재현하는 테스트나, “절대 0.15 이상 안 가는” 테스트를 안정적으로 통과시킬 수 있을 것입니다.

	결론:
		1.	LiveTradingEnvironment는 init_balance vs initial_capital를 일치시키면 TypeError 해결
	2.	드로우다운 테스트는 결정론적 crash 시나리오나 에이전트/리스크로직을 손봐서 항상 큰 낙폭(또는 낙폭 제한)이 발생하도록 해야 통과가 보장된다.
	3.	그 외에는 테스트 기준(예: 0.2 → 0.1)이나 crash_size를 조정하는 등으로 양쪽 로직을 맞추면 해결 가능합니다.

def generate_flash_crash_data_deterministic(
    length: int = 1000,
    crash_at: Optional[int] = None,
    crash_size: float = 0.3,  # 30% drop
    base_price: float = 100.0,
) -> pd.DataFrame:
    """Generate deterministic flash crash scenario data
    
    Args:
        length (int): Total number of periods
        crash_at (int, optional): Index at which crash occurs. If None, will be set to length//2
        crash_size (float): Size of crash as fraction of price (0.3 means 30% drop)
        base_price (float): Starting price level
        
    Returns:
        pd.DataFrame: OHLCV data with deterministic flash crash
    """
    if crash_at is None:
        crash_at = length // 2
        
    # Ensure crash_at has enough room
    crash_at = min(crash_at, length - 20)  # At least 20 periods for post-crash
    
    # Generate timestamps
    timestamps = pd.date_range(
        start="2024-01-01", periods=length, freq="5min"
    )
    
    # Initialize prices array
    prices = np.full(length, base_price)
    
    # 1) Pre-crash period: Gradual 10% rise
    for i in range(1, crash_at):
        prices[i] = prices[i-1] * 1.0005  # Small deterministic increase
        
    # 2) Crash point: Immediate 30% drop
    pre_crash_price = prices[crash_at - 1]
    crash_price = pre_crash_price * (1 - crash_size)
    prices[crash_at] = crash_price
    
    # 3) Post-crash: Additional 5% drop over 10 periods
    post_crash_periods = 10
    for i in range(crash_at + 1, crash_at + post_crash_periods):
        prices[i] = crash_price * (0.95 + 0.05 * (i - crash_at - 1) / post_crash_periods)
        
    # 4) Recovery period: Gradual rise
    for i in range(crash_at + post_crash_periods, length):
        prices[i] = prices[i-1] * 1.001  # Slow deterministic recovery
        
    # Generate OHLCV data with fixed spreads
    spreads = np.full(length, 0.001)  # 0.1% spread normally
    spreads[crash_at:crash_at + post_crash_periods] = 0.05  # 5% spread during crash
    
    # Generate volume with spikes during crash
    volumes = np.full(length, 100000.0)  # Normal volume
    volumes[crash_at:crash_at + post_crash_periods] *= 5  # 5x volume during crash
    
    data = pd.DataFrame(
        {
            "$open": prices,
            "$high": prices * (1 + spreads),
            "$low": prices * (1 - spreads),
            "$close": prices,
            "$volume": volumes,
        },
        index=timestamps,
    )
    
    return data

        max_drawdown_pct=0.3,

        data=data,
        risk_config=risk_config,
        initial_capital=10000.0
    )
    
    # Use a modified DummyStrategy that maintains full position until crash
    class CrashTestStrategy(DummyStrategy):
        def get_action(self, window_data):
            """Always maintain full long position until crash"""
            if len(window_data) < 2:
                return 1.0  # Start with full position
                
            current_price = window_data["$close"].iloc[-1]
            prev_price = window_data["$close"].iloc[-2]
            price_change = (current_price - prev_price) / prev_price

def check_trade(
        self,
        timestamp: pd.Timestamp,
        portfolio_value: float,
        trade_size: float,
        price: float,
        positions: Dict[str, float],
        asset: str,
        volatility: Optional[float] = None,
    ) -> Dict[str, Any]:
        """Check if trade is allowed and calculate adjusted size
        
        Args:
            timestamp: Current timestamp
            portfolio_value: Current portfolio value
            trade_size: Proposed trade size
            price: Current price
            positions: Current positions dictionary
            asset: Asset being traded
            volatility: Optional volatility estimate
            
        Returns:
            Dict containing:
            - allowed: Whether trade is allowed
            - adjusted_size: Adjusted trade size
            - reason: Reason for adjustment/rejection
        """
        # Check daily trade limit
        date_key = timestamp.date()
        if date_key not in self.trade_counter:
            self.trade_counter[date_key] = 0
            
        if self.trade_counter[date_key] >= self.config.daily_trade_limit:
            self.logger.warning(f"Daily trade limit reached for {date_key}")
            return {
                "allowed": False,
                "adjusted_size": 0.0,
                "reason": "Daily trade limit reached"
            }

        # Check drawdown
        if self.peak_value is not None:
            current_drawdown = (self.peak_value - portfolio_value) / self.peak_value
            if current_drawdown > self.config.max_drawdown_pct:
                self.logger.warning(
                    f"Max drawdown exceeded: {current_drawdown:.2%} > {self.config.max_drawdown_pct:.2%}"
                )
                # Force liquidation of all positions
                current_position = positions.get(asset, 0.0)
                if current_position != 0:
                    return {
                        "allowed": True,
                        "adjusted_size": -current_position,  # Liquidate entire position
                        "reason": f"Forced liquidation due to max drawdown: {current_drawdown:.2%}"
                    }
                return {
                    "allowed": False,
                    "adjusted_size": 0.0,
                    "reason": f"Max drawdown exceeded: {current_drawdown:.2%}"
                }

        # Calculate position value and check leverage
        position_value = abs(trade_size * price)
        current_exposure = sum(abs(pos * price) for pos in positions.values())
        total_exposure = current_exposure + position_value
        
        if total_exposure / portfolio_value > self.config.max_leverage:
            adjusted_size = max(0.0, (self.config.max_leverage * portfolio_value - current_exposure) / price)
            if adjusted_size < self.config.min_trade_size * portfolio_value / price:
                return {
                    "allowed": False,
                    "adjusted_size": 0.0,
                    "reason": "Leverage limit reached"
                }
            return {
                "allowed": True,
                "adjusted_size": adjusted_size,
                "reason": "Adjusted for leverage limits"
            }

        # Check position size limits
        max_position_value = portfolio_value * self.config.max_position_size
        if position_value > max_position_value:
            adjusted_size = max_position_value / price
            if adjusted_size < self.config.min_trade_size * portfolio_value / price:
                return {
                    "allowed": False,
                    "adjusted_size": 0.0,
                    "reason": "Position size too large"
                }
            return {
                "allowed": True,
                "adjusted_size": adjusted_size,
                "reason": "Adjusted for position size limits"
            }

        # Check minimum trade size
        min_trade_value = portfolio_value * self.config.min_trade_size
        if position_value < min_trade_value:
            return {
                "allowed": False,
                "adjusted_size": 0.0,
                "reason": "Trade size below minimum"
            }

        # All checks passed
        return {
            "allowed": True,
            "adjusted_size": trade_size,
            "reason": "OK"
        }

테스트(test_drawdown_limits)가 기대하는 것은 “드로우다운이 5%를 넘으면, 추가 거래를 막아서 success=False가 되어야 한다”는 로직입니다. 그러나 현재 RiskManager는 drawdown이 초과되면 warning만 찍고, 거래를 실제로는 허용(allowed=True)하고 있습니다.

1. 왜 그런가?
	•	로그상, RiskManager는 Max drawdown exceeded: 7.09% > 5.00%라고 여러 번 경고하지만, 결정적으로 check_trade() 로직에서 return {"allowed": True, ...} 처리를 계속 해주는 것 같아요.
	•	따라서 백테스터에서 해당 거래가 그대로 체결( success=True )되고, 테스트는 “이 거래는 실패해야 한다( success=False )”라고 했으니 어긋납니다.

2. 해결책: RiskManager에서 drawdown 초과 시 거래를 실패 처리

2.1. check_trade()에서 드로우다운이 초과되면 allowed=False로 반환

예를 들어, risk_manager.py (또는 비슷한 파일)에 있는 RiskManager.check_trade() 안에서:

current_drawdown = (self.peak_value - portfolio_value) / self.peak_value

if current_drawdown > self.config.max_drawdown_pct:
    self.logger.warning(
        f"Max drawdown exceeded: {current_drawdown:.2%} > {self.config.max_drawdown_pct:.2%}"
    )
    return {
        "allowed": False,
        "adjusted_size": 0.0,
        "reason": f"Drawdown {current_drawdown:.2%} > {self.config.max_drawdown_pct:.2%}"
    }

처럼 강제로 allowed=False를 반환하면, 백테스터 쪽에서는 “risk_check[‘allowed’] == False”일 때 거래를 거부하고 success=False로 처리해야 합니다.

즉,

if not risk_check["allowed"]:
    return {
        "timestamp": timestamp,
        "symbol": asset,
        "price": current_price,
        "amount": 0,
        "fee": 0,
        "success": False,
        "reason": risk_check["reason"]
    }

이런 식으로 백테스터가 결과를 만들 것입니다.

2.2. 현재 코드에서 drawdown 초과 시 경고만 찍는 로직 확인

이미 “Max drawdown exceeded: 7.09% > 5.00%” 같은 warn이 뜨는 걸 보면, RiskManager 어딘가에서

if current_drawdown > self.config.max_drawdown_pct:
    self.logger.warning(...)

를 하고 있지만, 그 다음에 계속 return {"allowed": True, ...}를 하는 구조일 가능성이 큽니다.

이를 (1) “경고 + 거래 거부”로 바꾸거나, (2) “경고 + position 강제 청산”으로 바꾸면 됩니다.

3. 테스트를 충족하기 위해 필요한 최소 변경 요약
	1.	RiskManager.check_trade():

if current_drawdown > self.config.max_drawdown_pct:
    self.logger.warning(
        f"Max drawdown exceeded: {current_drawdown:.2%} > {self.config.max_drawdown_pct:.2%}"
    )
    return {
        "allowed": False,             # 거래 불허
        "adjusted_size": 0.0,
        "reason": "Max drawdown exceeded"
    }

	2.	백테스터(execute_trade 등)에서 risk_check["allowed"] == False면 success=False 처리:

if not risk_check['allowed']:
    return {
        'timestamp': timestamp,
        'symbol': asset,
        'price': current_price,
        'amount': 0,
        'fee': 0,
        'success': False,
        'reason': risk_check['reason']
    }

	3.	그러면 드로우다운 > 5% 상태에서 시도한 두 번째 거래가 실패(success=False)로 찍힐 것이고,

AssertionError: False is not true

에서 assert result2['success'] is False가 통과하게 됩니다.

4. 그 외 고려 사항
	•	만약 기존에는 “드로우다운이 5% 넘었어도 거래는 가능하게 두고 싶다”는 설계였다면, 지금 테스트 요구사항과 상충됩니다.
	•	그럴 땐, 테스트 로직을 바꿀지(“경고만 찍히고 거래는 허용된다면 success=True여도 괜찮다”) 혹은 RiskManager 로직을 바꿀지 의도에 맞춰 결정해야 합니다.
	•	통상 RiskManager가 “드로우다운 한도 넘으면 매수(롱) 추가 불가 / 청산만 허용” 같은 로직으로도 구현할 수 있습니다. 예:

if current_drawdown > self.config.max_drawdown_pct:
    if trade_size > 0:  # 매수 증가?
        # 거부
        return {"allowed": False, "adjusted_size": 0.0, "reason": "Drawdown exceeded - no more buys"}
    else:
        # 매도 or 0?
        # 허용해서 포지션 줄이기
        return {"allowed": True, "adjusted_size": trade_size, "reason": "OK - reducing position"}

이런 식이면, “드로우다운 초과 시 추가 매수만 막고, 포지션 정리는 허용”이 가능합니다.

	•	하지만 현재 테스트는 “두 번째 거래가 success=False여야 한다”를 강하게 요구하므로, “아예 거래 불가” 형태가 맞겠습니다.

결론

**테스트가 “드로우다운 5% 초과 시 두 번째 거래가 실패해야 한다”**고 주장한다면,
RiskManager에서 드로우다운 초과 시 allowed=False 반환 → 백테스터가 success=False 처리 → test_drawdown_limits 통과.

즉, check_trade()에서 warn만 찍지 말고 allowed=False로 돌려주면 이 문제는 해결됩니다.
