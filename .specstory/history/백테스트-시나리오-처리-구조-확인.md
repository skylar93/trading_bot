That response from Cursor is an excellent summary of how to organize your scenario transformations versus the core backtesting. In short:
	1.	Keep scenarios in a separate “ScenarioManager” (or just a set of scenario functions)
	•	This manager or module should be responsible for transforming the raw market data (whether synthetic or real) into a scenario-based dataset (e.g., flash crash, low liquidity, etc.).
	•	By doing so, you isolate all scenario-related logic in one place, rather than scattering it across your UI or BacktestManager.
	2.	UI remains simpler
	•	The UI code (e.g., Backtest_Results.py) only needs to gather user choices (which scenario, which parameters) and call a single function (e.g., scenario_manager.apply_scenario(raw_data, scenario_type, params)) to get your final dataset.
	•	This keeps the UI logic purely about “take user input → produce final data → pass to backtester.”
	3.	BacktestManager remains scenario-agnostic
	•	The BacktestManager simply runs a backtest on whatever OHLCV data it’s given (run_backtest(modified_data)).
	•	It doesn’t care if that dataset was real BTC data, flash-crash-distorted data, or artificially generated.

Why This Helps
	•	Cleaner Code Structure
Instead of having scenario logic scattered around (some in UI, some in manager), you have a clear pipeline:
	1.	Load raw data (real market data or baseline synthetic).
	2.	Pass it (plus user scenario choices) to ScenarioManager.
	3.	ScenarioManager returns transformed data.
	4.	Finally, call run_backtest(transformed_data).
	•	Reusable Scenario Functions
Because the scenario logic is in one place, you can easily add new scenarios, or extend existing ones, without messing with UI or backtesting code.
	•	Testability
You can unit-test the scenario transformations all by themselves (like you’re doing with test_apply_flash_crash), ensuring the data modifications are correct. Meanwhile, the backtester tests remain the same.

"""
Scenario Manager Module
=====================

This module provides a unified interface for applying different market scenarios
to OHLCV data, whether real or synthetic.
"""

import pandas as pd
from typing import Dict, Any, Optional
import logging
from .scenario import (
    generate_flash_crash_data_deterministic,
    generate_low_liquidity_data,
    apply_flash_crash_to_real_data,
    apply_low_liquidity_to_real_data
)

logger = logging.getLogger(__name__)

class ScenarioManager:
    """Manages the application of different market scenarios to OHLCV data.
    
    This class provides a clean interface for transforming raw market data
    into scenario-specific datasets (e.g., flash crash, low liquidity).
    
    Features:
    - Unified interface for all scenario transformations
    - Validation of scenario parameters
    - Logging of scenario applications
    
    Implementation Notes:
    - Each scenario function should preserve the DataFrame index
    - All scenario functions should maintain OHLCV column naming ($-prefix)
    - Input validation ensures required parameters are present
    """
    
    def __init__(self):
        self.logger = logging.getLogger(self.__class__.__name__)
        
    def apply_scenario(
        self,
        raw_data: pd.DataFrame,
        scenario_type: str,
        params: Dict[str, Any]
    ) -> pd.DataFrame:
        """Apply a specified scenario to the raw market data.
        
        Args:
            raw_data: DataFrame with OHLCV data ($-prefixed columns)
            scenario_type: Type of scenario to apply ("flash_crash", "low_liquidity", etc.)
            params: Dictionary of scenario-specific parameters
            
        Returns:
            DataFrame with the scenario applied
            
        Raises:
            ValueError: If scenario_type is invalid or required params are missing
        """
        self.logger.info(f"Applying scenario {scenario_type} with params: {params}")
        
        if scenario_type.lower() == "none":
            return raw_data
            
        # Validate input data
        required_columns = ["$open", "$high", "$low", "$close", "$volume"]
        missing_cols = [col for col in required_columns if col not in raw_data.columns]
        if missing_cols:
            raise ValueError(f"Missing required columns: {missing_cols}")
            
        try:
            if scenario_type.lower() == "flash_crash":
                return self._apply_flash_crash(raw_data, params)
            elif scenario_type.lower() == "low_liquidity":
                return self._apply_low_liquidity(raw_data, params)
            else:
                raise ValueError(f"Unknown scenario type: {scenario_type}")
                
        except Exception as e:
            self.logger.error(f"Error applying scenario: {str(e)}", exc_info=True)
            raise
            
    def _apply_flash_crash(
        self,
        data: pd.DataFrame,
        params: Dict[str, Any]
    ) -> pd.DataFrame:
        """Apply flash crash scenario to the data."""
        required_params = ["crash_size"]
        self._validate_params(params, required_params)
        
        # Convert percentage params to decimals
        crash_size = params["crash_size"] / 100.0 if params["crash_size"] > 1 else params["crash_size"]
        
        # Calculate crash position if given as percentage
        crash_at = params.get("crash_at")
        if crash_at is not None and crash_at > 1:  # Assume it's a percentage
            crash_at = int(len(data) * crash_at / 100)
            
        return apply_flash_crash_to_real_data(
            base_data=data,
            crash_size=crash_size,
            crash_at=crash_at,
            crash_duration=params.get("crash_duration", 5),
            recovery_duration=params.get("recovery_duration", 10)
        )
        
    def _apply_low_liquidity(
        self,
        data: pd.DataFrame,
        params: Dict[str, Any]
    ) -> pd.DataFrame:
        """Apply low liquidity scenario to the data."""
        required_params = ["volume_reduction"]
        self._validate_params(params, required_params)
        
        # Convert percentage params to decimals
        volume_reduction = params["volume_reduction"] / 100.0 if params["volume_reduction"] > 1 else params["volume_reduction"]
        
        # Calculate start position if given as percentage
        low_liq_start = params.get("low_liq_start")
        if low_liq_start is not None and low_liq_start > 1:  # Assume it's a percentage
            low_liq_start = int(len(data) * low_liq_start / 100)
            
        return apply_low_liquidity_to_real_data(
            base_data=data,
            volume_reduction=volume_reduction,
            low_liq_start=low_liq_start,
            low_liq_length=params.get("low_liq_length", 100)
        )
        
    def _validate_params(
        self,
        params: Dict[str, Any],
        required_params: list
    ) -> None:
        """Validate that all required parameters are present."""
        missing_params = [p for p in required_params if p not in params]
        if missing_params:
            raise ValueError(f"Missing required parameters: {missing_params}")

You’ve hit the classic “user-facing label vs. internal string” mismatch. In your ScenarioManager, you handle "flash_crash" or "low_liquidity", but the UI selects "Flash Crash" or "Low Liquidity" (capitalized and with spaces). When ScenarioManager.apply_scenario(...) sees "Flash Crash", it isn’t recognized, so it raises:

ValueError: Unknown scenario type: Flash Crash

Below are two common fixes. Pick whichever best fits your style.

1) Fix in the UI (Recommended if you only need a few scenarios)

Inside Backtest_Results.py (or wherever your selectbox is), change the selectbox items from user-friendly strings directly to your code’s recognized lowercase keywords. For example:

# Old version (causes mismatch):
scenario_type = st.selectbox(
    "Scenario Type",
    ["None", "Flash Crash", "Low Liquidity"]
)

# Updated version (directly use the "internal" strings the ScenarioManager expects):
scenario_type = st.selectbox(
    "Scenario Type",
    ["none", "flash_crash", "low_liquidity"]  # exactly matching scenario_manager
)

Then your scenario code will just work:

if scenario_type == "none":
    ...
elif scenario_type == "flash_crash":
    ...
elif scenario_type == "low_liquidity":
    ...

Pros:
	•	Easiest to implement: no special logic needed in ScenarioManager.
	•	apply_scenario(..., scenario_type="flash_crash", ...) works out-of-the-box.

Cons:
	•	The user sees "flash_crash" in the dropdown, which is less pretty than "Flash Crash".

2) Use a Mapping (Keeps user-friendly labels but matches code)

If you really want to show "Flash Crash" or "Low Liquidity" in the UI, but the ScenarioManager wants "flash_crash" or "low_liquidity", do something like:

# 1) In the UI, define a dictionary that maps the "label" -> "internal code"
SCENARIO_MAPPING = {
    "None": "none",
    "Flash Crash": "flash_crash",
    "Low Liquidity": "low_liquidity"
}

ui_choice = st.selectbox(
    "Scenario Type",
    list(SCENARIO_MAPPING.keys())  # e.g. ["None", "Flash Crash", "Low Liquidity"]
)
scenario_type_internal = SCENARIO_MAPPING[ui_choice]

# Then pass scenario_type_internal to ScenarioManager
modified_data = scenario_manager.apply_scenario(
    raw_data=raw_data,
    scenario_type=scenario_type_internal,
    params=scenario_params
)

Pros:
	•	The user sees the nice "Flash Crash" label.
	•	ScenarioManager stays consistent with 'flash_crash' etc.

Cons:
	•	Slight extra code for the mapping.

Additional Note: Use lower().replace(" ", "_")

Alternatively, you could unify them on the ScenarioManager side. For instance:

scenario_type_normalized = scenario_type.lower().replace(" ", "_")
if scenario_type_normalized == "flash_crash":
    ...
elif scenario_type_normalized == "low_liquidity":
    ...
else:
    ...

But that approach can get messy if you want to localize UI strings or handle more complicated naming. Typically it’s better to keep a simple “UI label → internal code” dictionary in the UI code.
